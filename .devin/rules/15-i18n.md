# Rule: i18n & Localization for All Projects

**ALWAYS** apply the i18n & Localization skill and workflow when building multi-lingual web applications. Internationalization is architecture — build i18n-ready from day one, even if you only launch in one language.

## Skill
`~/.codeium/windsurf/skills/i18n-localization.md`

## Workflow
`~/.codeium/windsurf/windsurf/workflows/i18n.md` — invoke with `/i18n`

## Sub-Agent
`~/.codeium/windsurf/windsurf/sub-agents/i18n-specialist.md` (parent: Design Engineer)

## How to follow this rule:
1. When building multi-lingual apps, invoke the `/i18n` workflow
2. Follow the workflow steps in order: Assess → Library → Routing → Files → ICU → Formatting → RTL → SEO → Management → Content → Testing → Document
3. Always use ICU MessageFormat for pluralization, gender, and variables
4. Always use `Intl` API for date, number, currency formatting — never hardcode formats
5. Always use CSS logical properties for RTL support — never physical properties
6. Always add hreflang tags and localized metadata for SEO
7. Always set up a translation management workflow with CI/CD integration
8. Always test with pseudo-localization, missing key detection, and RTL visual testing

## When this rule applies:
- Building a multi-lingual website or app
- Adding a new language to an existing app
- Setting up RTL support
- Implementing locale-aware formatting
- User asks about i18n or localization

## When this rule does NOT apply:
- Single-language projects with no plans for localization
- User explicitly says to skip i18n
